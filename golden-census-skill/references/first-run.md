# The first run

Open this file when you write a manifest for the first time. Eight steps take a program from no manifest to a committed golden, one mutant caught, and the first hand-back. Each step ends with the command and the line that proves it done. Run them in this order. After step 8 the loop is `SKILL.md` alone; open `references/rebaseline.md` the next time the manifest, the census, the runner or the intended output changes.

## The first run, in order

1. **Choose the inputs and the surfaces.** This step is a rule, not a command. A program that is already a command is its own candidate, and the rule below is all that step 1 asks of it. A candidate is a function whose inputs you can save to a file. Its value must be one a JSON encoder can write. Nothing else may reach its output: no clock, no random source, no network, no unordered collection. Step 5 is the proof. Under `--twice`, the line `two captures of one subject differ: <path> line N` names what the function read for itself. To record a program properly, give it enough inputs that the runs exercise the logic a change could break. At least three: the ordinary case, an empty case, and a case the program refuses. An input that lives outside the subject's root is reached through `<WORK>`, by a `[[setup]]` step that links or copies it. Or pin it as a `git`/`sha` input and spell it `<CLONE>/…`. Never spell it as an absolute path in `args`: `surfaces.json` records the argv, and no `regex` fold reads that file (`references/census.md`, "`regex`"). Never spell it as a relative path out of root: `mutants` runs the subject from a clone under the temp root, where `../` names something else. A pinned input records the commit's tree. Uncommitted edits are not in it, and the golden does not move while they change. An input reached through `<WORK>` records the tree as it is when the capture runs, uncommitted edits included, and moves when they do. Choose the pin to record a fixed codebase and `<WORK>` to record the working tree, and say in your report which you chose. One surface per documented output; for a command, `--help` and a refusal included. Run each input through a surface or two by hand, twice; what differed between the two runs is what the census folds or pins.
2. **`init`.** Run `golden-census init <DIR> --template <NAME>`. `golden-census init --list` names the templates. A program that runs from a command line: run `golden-census init <DIR>` alone; it needs no runner. Code with no command line of its own, in a language with no template: the same, then write the runner yourself to the six steps in `references/templates.md`, "A language with no template". `init` prints the list of holes, then one closing line. Fill every hole above that line.
   - A hole left in the runner is not refused. The capture records it as a failing row, a non-zero exit of the subject, and the capture itself exits 0. Fill the runner's holes next; step 3 probes it before the manifest's holes are filled.
   - `<DIR>` is the subject's checkout, or any directory whose manifest spells `root` from there. `init` creates it if it is absent and overwrites nothing. A manifest kept outside the checkout spells `root` as the relative path to it, such as `"../../myapp"`, and every other path in the manifest stays relative to the manifest.
   - `init` writes in two passes: the neutral three, then the template's runner and wrapper. It is all or nothing across both. A refusal, or a reader that stops reading its output, leaves nothing behind: the files go, and so does every directory `init` made on the way; a directory that already existed stays. A refusal's `next:` line says what to do.
   - The subject is ONE repository. Never `git init` a directory inside it. Step 7 says what that costs.
   - The `python-function` runner lands beside the manifest: spell it `<HERE>/runner.py`, where `<HERE>` is the manifest's own directory wherever the manifest sits. The Swift runners land in the literal `<<HOLE:TEST_TARGET_DIR>>/` directory and are moved; `references/templates.md` says where. A relative element of `[subject] command` resolves under `root`.
   - Open the template's README here: `references/templates.md` says where it is and which sections to read.
3. **`probe` — before the first `capture`.** The rule: probe the command before a capture records it. Then nothing false is ever recorded as a golden.
   - Run `golden-census probe -- <the command> '<WRITES>'`. It prints `  5/5 passed` and exits 0.
   - The command is the manifest's future `[subject] command`. For a script it is `<interpreter> <script>`. For a compiled tool it is the tool. For a template's runner, `references/templates.md` gives each template's probe line.
   - Quote `<WRITES>`. A shell reads the angle brackets as a redirection.
   - Run it from the directory where the command's relative paths resolve: `probe` runs the candidate in the current directory and has no `root`. For the `python-function` runner that is the manifest's directory, where `runner.py` is; for `swift test` it is the directory holding `Package.swift`, the manifest's `root`. From anywhere else a relative path resolves to the wrong place, and clause 1 fails because the path was wrong, not because the program is unfit.
   - Spell a Python interpreter by the path of the one running golden-census, so the banner folds it to `<PYTHON>`: `python3 -c 'import sys; print(sys.executable)'` with the `python3` that runs it, or `head -1 "$(command -v golden-census)"` for an installed command. A symbolic link to that interpreter, such as a package manager's `python3` link, is printed as given, not folded.
   - For a template's runner: fill the runner's holes, probe it, then fill the manifest's holes (step 4). Running `census` before the runner's `probe` is harmless: only a hole in the manifest or the census gates it. No command refuses a hole in a template's runner. Only `mutants` refuses a hole in the mutants file.
   - A runner whose hole is filled wrong is a golden of the wrong function. Examples are the wrong `MODULE` and a `FUNCTION_CALL` that calls the wrong thing. golden-census records it as faithfully as a golden of the right one. `probe` on the runner catches that.
   - A program that only prints is still a subject. `probe` needs a file, so hand it a shell that writes one: `golden-census probe -- sh -c 'mytool --json > "$1"' _ '<WRITES>'`. The shell and its redirection are for the probe only. The manifest names the program itself, with no shell, and `capture --twice` (step 5) is its determinism proof once the manifest exists.
   - A tool that prints findings and exits non-zero keeps every clause. Clause 3 fails only a run that exited 0 and wrote no file; it never asks the code to be 0 and never compares the two runs' codes.
   - Before anything is recorded, the probe will report if the program outputs the absolute path of the directory where it is running. The probe will turn clause 4 red because the absolute path is machine data leaking into the output. golden-census normalizes output to remove machine data, so a capture would fold that path to `<REPO>` and pass. If the program is intended to print an absolute path, record this in the census's `root` fold `finding`.
   - A program that resolves and prints the path of an input it was handed, such as a scanner given a directory, is red at clause 4 on that path, and no `probe` flag folds it. That red is the input's, not the program's: the manifest reaches the input through `<CLONE>` or `<WORK>`, the capture folds that directory, and `capture --twice` (step 5) is the proof, as it is for `swift-package`.
   - `references/templates.md` says what each template's `probe` prints. The `swift-package` runner is red at clause 4 on `swift test`'s own timestamps, even with `--census`; that file says why the red is expected, and step 5 is its proof instead. `references/verdicts.md` reads any other red block.
4. **Fill the holes.** Run `golden-census census --manifest <MANIFEST>`. It prints the census controls as a block with their tally, then `census <REPO>/…/census.toml`, the rows, the preconditions and the `census state` block. Exit 0. While a hole is open, it prints `REFUSED: the manifest … still carries the unfilled hole(s) <<HOLE:…>>` instead. The refusal names every hole left and the file it is in.
   - The manifest's own placeholders are `<ROOT>`, `<WORK>`, `<WRITES>` and `<PYTHON>`; `references/manifest.md` lists the rest. They are not holes: leave them as written. `<REPO>`, `<TMPROOT>` and the other tokens in printed lines are folds, never written into a manifest; `SKILL.md`, "Reading the verdict", lists them.
   - A surface that prints a time needs the `TZ` pin as well as the clock pin; the template has both, commented. A fixed instant still renders in the machine's zone, and `--twice` cannot see a zone that does not change between its two runs.
   - A census made by `init` folds two of the four directories golden-census knows, `root` and `work`; the `clone` and `fixed-width-dir` fold rows sit commented in the file. A capture then prints one line under its header, ``census note: no `path` fold names clone, fixed-width-dir. If a captured file prints one of those directories, the contraband scan refuses the capture.`` `census` prints the same sentence as `note:` under its rows. It is a fact, not a finding. When a capture is refused for leaking one of those directories, the refusal names the `path` row to add: uncomment it.
   - A subject that is not a git checkout stops here: the neutral census's `git-checkout` precondition refuses it. Make the tree a repository, which step 7 needs anyway, or delete that row. A `precondition` row does not become a `state` row by changing one key: `state` takes `variables`, `commands` or both, and no other key, so the row is refused as a whole (`references/census.md`).
5. **`capture --twice`.** Run `golden-census capture --manifest <MANIFEST> --out <GOLDEN> --twice`. It prints `  --twice: N files, byte-identical` and exits 0.
   - When some rows did not run or printed nothing, the capture still prints `--twice: N files, byte-identical`. The lines under it, opening `K of N rows recorded no output from the subject:`, name each such row and why. A row named there gives the golden no evidence. Fix what the reason names and capture again, or say in your report why that row is meant to be empty.
   - Some surfaces may change occasionally, even with the same input. (Examples: a renderer's output, a program that calls an LLM, and a program that prints parallel results in the order they finish.) A row that passes `--twice` and then moves in a later run is likely such a surface. Leave the surface out, or pin or fold what moves, and say why in your report.
   - A subject that prints its own git state, a commit sha or a `clean`/`dirty` word, moves every such row at every commit and during every uncommitted edit. Fold the sha with a `regex` row, or both fields of a JSON stamp with the `json-fields` row that the neutral census carries as a commented example; `references/census.md` has both.
   - Commit `<GOLDEN>` beside the manifest, the census and the mutants file. The golden IS the handoff. Step 7 reads the committed tree, and the mutants file's `GOLDEN` hole must name this same directory: `<HERE>/golden` when it sits beside that file.
   - `init` writes no `.gitignore`: a scratch capture goes in a scratch directory of yours, such as `/tmp/before`, never in the tree.
   - `TMPDIR`, when set, is an absolute path of at most 49 characters; a wider one is refused when the command opens its work directory, after the census's controls have run and before any row of the subject runs. The controls run under a wide root, and mark the fixed-width pin's real-directory arm `[SKIP]`. `references/machine.md` has the temp-root rules, the clone cache and the git settings. Open it on any refusal that names `TMPDIR`, `HOME` or a cache directory.
6. **`compare`.** Run `golden-census compare --manifest <MANIFEST> --golden <GOLDEN>`. It prints `  IDENTICAL` under `N golden files, N new files` and exits 0. The command makes a fresh capture. `--against <DIR>` compares a capture already recorded instead (step 8). `--command ARG`, one flag per element of an argv, runs the fresh capture with that argv in place of the manifest's `command`: use it to compare a built copy, say, a bundle, with the golden the source recorded. The `COMPARE` block prints `command:` under `new:`; quote it with the verdict. `IDENTICAL` then says that argv printed what the golden recorded. `--command` is refused with `--against`.
7. **One mutant.** Fill the mutants file's holes with one edit a check must catch; its `find` must match the committed text exactly once. Commit any edit of the subject first. A subject whose `git status` is already clean needs no commit. Commit the golden when it sits inside the subject's repository, since a golden named `<HERE>/golden` is read where it is, committed or not. Then run `golden-census mutants --manifest <MANIFEST> --mutants <MUTANTS>`. It prints `  1/1 mutants caught by every check they expect` and exits 0.
   - `mutants` clones the COMMITTED tree. An uncommitted edit of the subject is invisible to it. The golden is read where `golden` points: `<HERE>/golden` beside the mutants file as it stands, committed or not; a bare path inside the clone, so committed.
   - That tree must CONTAIN the subject. A repository `git init`-ed inside the subject's checkout clones only itself and carries nothing to mutate. The null mutant then comes back not SILENT, and that is the sign.
   - `references/mutants.md` has the mutant row, the rules for `file`, and the cwd rule of a `command` check. Its trap: a check that runs beside the mutants file imports the UNMUTATED package and stays SILENT on every mutant.
8. **Before every hand-back: `compare`.** Run step 6 again and report it as `SKILL.md` says under "Before every hand-back" and "Report hygiene". From here on `SKILL.md` is the whole loop: `compare` before you touch a surface and `compare` before you hand back. The next change to the manifest, the census, the runner or the intended output is `references/rebaseline.md`.
