# Known issues and cautions

Everything here was reproduced against the released code by running the tool, on the date given. A **known issue** is a case where the tool gives a wrong result in silence: an `IDENTICAL`, an `[OK]`, an exit 0 or a golden written, with no sentence saying what went wrong. Each is an open defect of the released code and stays here until its fix ships. A **caution** is a situation the tool answers loudly, or one that takes an input nobody makes on purpose; it is handled by not doing it, and the entry says what happens if you do.

Each entry gives the case, what the tool does, and what to do instead.

Verified 2026-10-13; the entries added 2026-10-19 were reproduced that day at `675ebf1`; the entries added 2026-10-26 were reproduced 2026-10-25 at `83df4a9`.

## Known issues

- **A `tallies` group whose body is a single tally line.** The group is a banner, a rule, `3/3 passed` and a rule. The tool reads the tally line as a banner. The golden records `Group A: <no tally line>` and `3/3 passed: <no tally line>`. Have each group print a check line above its tally, or record the output through a `run` surface.
- **`probe` passes a command whose exit code changes between its two runs.** Both runs write their file. Clause 3 reports `[PASS]` with `exit codes [0, 3]`. Read the `actual:` line of clause 3, not only its verdict.
- **A global git setting that changes what a checkout writes.** The global configuration sets `core.symlinks = false`, or a `smudge` filter that the pinned repository's `.gitattributes` names, with a `clean` that undoes it. The clone of the pinned input holds a file with the link's target name as its text, or the smudged text. The log says the clone is `clean`, and the capture completes at exit 0. A compare under the same configuration is `IDENTICAL`. Capture under a global configuration that sets neither.
- **A pinned input that cannot be cloned for a mutant after the null mutant cloned it.** The clone cache is removed and the pinned repository moved away while `mutants` runs, after the null mutant's checks. The mutant's comparator capture records the input as a SKIP and compares it with the golden. A mutant that changes only a comment then reads `FIRED`, with `1/1 mutants caught by every check they expect`, at exit 0. No line names the skipped input. Change nothing in the clone cache or the pinned repository while `mutants` runs.

## Cautions

- **Under `probe -- sh -c '<program> … > "$1"' _ '<WRITES>'`, a program the shell cannot find still passes.** The shell makes the file, empty, and both runs exit 127 alike, so every clause holds: `5/5 passed`, exit 0. Read clause 3's `actual: exit codes` line; `127` is the shell saying the program was not found. Run the program by hand once before probing it through a shell.

- **Run one golden-census command at a time against a subject, and change nothing under the subject, the golden directory or the temp root while it runs.** A second capture of the same pinned input, started at the same moment, is skipped with "File exists" until the first has cached the clone. A file you edit while a command runs is read in the state it has when the run reaches it. Start the second command after the first finishes. See the manual.
- **Do not spell `<WRITES>` or `<CLONE>` where it has no value.** The cases are `<WRITES>` in the `args` or `env` of a surface that has no `writes` key, and `<CLONE>` in a `drift` command or in a `counter` of a manifest with no cloned input. The manifest or census check accepts each case. The tool refuses it when it runs, with "has no value in this run", after earlier rows have run. Spell `<WRITES>` only on a surface with `writes`, and `<CLONE>` only in a manifest with a cloned input.
- **Do not save an `--allow-diff` table with a UTF-8 byte-order mark, or as UTF-16 without one.** The first row, or every row, is then not permitted, and the comparison reports those rows as differing. The only sign is the `unused:` line, which shows the table's row with its stray bytes. A UTF-16 file with its byte-order mark is refused as not UTF-8 text. Save the table as UTF-8 without a byte-order mark.
- **Do not pin a commit that checks out dirty on your disk.** An example is a commit with two files whose names differ only by case, on a case-insensitive volume. The tool skips the input and says the clone "is not clean". Its advice to delete the clone does not help, because the next clone is dirty again. Pin a commit that checks out clean on your disk.
- **Do not give a `command` precondition that reads standard input.** Every command gets an empty one, so the tool refuses the precondition when it runs. The advice to run the command by hand does not reproduce the failure, because by hand the command reads your input. Give the command its input as an argument or a file.
- **Spell `clean` as a bare boolean.** `clean = "false"`, a quoted string, is read as true. The refusal prints `clean = true` and advises setting `clean = false`, which the row already says. Write `clean = false` without quotes.
- **Do not put a key of the other precondition kind on a `git-checkout` or `command` row.** The tool accepts such a key and never reads it. Keep each row to the keys of its own `check`.
- **Do not print the base name of a file the command wrote under `probe`.** A command that prints `wrote report.json` fails `probe`'s clause 4, "stdout moved between the runs". `probe` writes its two runs to `out-1` and `out-2`, so the base name differs between them. A capture is not affected, because a surface's `writes` name is stable. Print the full path, which is folded, or read that `[FAIL]` for what it is.
- **Spell `root` with the letter case the file system uses.** A root typed in another case is not folded. Under the home directory or the temp root, the capture refuses with advice to add a `regex` fold. Elsewhere, the machine path reaches the golden. Copy the spelling that `ls` prints.
- **Do not put a `[files]` entry on the way to a `writes` path.** The manifest has `[files."a"]` and a surface with `writes = "<WORK>/a/b.json"`. The `census` command accepts it. `capture` runs the controls and then refuses the row, saying it "could not clear that path before the run: NotADirectoryError: Not a directory". That sentence names the operating system's error, not the two keys. Its `next:` line names a `[files]` entry as one cause. Give `writes` a path that no `[files]` entry makes a directory of.
- **Do not ignore files through the repository's own `core.excludesFile`.** The subject's `.git/config` sets `core.excludesFile` to a file that lists `junk.txt`, and the census has a `git-checkout` precondition with `clean = true`. Plain `git status --porcelain` prints nothing. golden-census refuses the precondition and quotes `?? junk.txt`. It runs git with `core.excludesFile=/dev/null`, which overrides the repository's setting as well as the global one. List the file in `.gitignore` or `.git/info/exclude`, which golden-census honors.
- **Spell a `drift` control's `output` without `..`.** The control's command makes `a` a link to `sub/x` and writes `a/../b`, which lands at `<WORK>/sub/b`. With `output = "<WORK>/a/../b"`, the control reads `<WORK>/b` and finds no file. It fails with `pinned 0B/0B` and advice to point the control at a command that stamps the time. The same command passes with `output = "<WORK>/sub/b"`. Name the file the command writes by its own path.
- **Refusals that name the wrong cause or give advice that does not help.** Each item was reproduced.
  - A `git` that prints a byte that is not UTF-8 ends in a refusal, or an input's SKIP, saying the command "ran and printed a byte no UTF-8 decoder can read". The advice is to make that command print UTF-8, which you cannot do for `git`. Run the `git` command that the message names by hand, and repair that `git`.
  - A pinned input that cannot be cloned in a `mutants` run ends in the same null-mutant refusal, and the refusal says nothing of the clone. Run `capture` and read the `[SKIP]` line of the input.
  - A refused census control is followed by lines about "the rows above" and "the FAILED control(s)", although no control failed. Read the `REFUSED:` line of the control.
  - A usage error that the parser answers itself goes to standard error in its own words, at exit 2, with no `REFUSED:` and no `next:` line. An example is `golden-census capture: error: the following arguments are required: --out`. Read that line.
  - A refusal's `ran:` and `about to run:` lines fold the temp root with the census's `work` token, not the work directory. Under a census whose `work` fold is spelled `<WORK>`, `REFUSED: b/s writes <WORK>/out.txt` stands over `ran: … <WORK>/golden-census-hvfaysl3/out.txt`. Both lines name one file. Read the path in the `REFUSED:` line.
  - Under `mutants`, a null-mutant refusal for contraband quotes at most 20 hit lines and gives no count. A subject that prints 22 home paths shows 20 lines. `capture` of the same subject prints `22 hit(s)` on its scan line. Run `capture` to see the count.
